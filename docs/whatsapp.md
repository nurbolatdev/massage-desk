# WhatsApp integration

Official **WhatsApp Cloud API** by Meta. Unofficial clients are not used: they violate WhatsApp terms and risk a ban of the master's number.

- **24-hour window:** free-form replies while `now < last_inbound_at + 24 h` (`conversations.last_inbound_at`); at exactly 24 h or later, or when the client has not sent any message yet, the window is closed and only approved templates can be sent.
- **Templates** (reminders, confirmations) need Meta approval.
- **Interactive messages:** reply buttons (up to 3) and lists — service, day and time selection.
- **Pricing:** client-initiated service conversations are free; templates outside the window are paid.

## Webhook

- `GET /webhook/whatsapp` ✅ — Meta endpoint verification (`WHATSAPP_VERIFY_TOKEN`, constant-time comparison).
- `POST /webhook/whatsapp` ✅ — verifies `X-Hub-Signature-256` (`sha256=` + HMAC-SHA256 of the raw body keyed by `WHATSAPP_APP_SECRET`, constant-time comparison):
  - missing or wrong signature, or an empty `WHATSAPP_APP_SECRET` → `403` without parsing the body;
  - body larger than 3 MiB → `413`;
  - every delivery attempt writes a row to `webhook_logs` (signed JSON object → `received` with `payload`; refused → `rejected` without `payload`; signed body that is not a JSON object or contains `\u0000` → `200` and `failed`);
  - a signed JSON object (`received`) is then processed in a separate transaction and updated with `processed_at` to `processed`, `duplicate` (every storeable message in the delivery was already stored), or `failed` (`error` holds the exception class name, `payload` is kept for replay, and the HTTP response is still `200`);
  - only `entry[].changes[]` with `field = "messages"` and `value.messages[]` of types `text`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `contacts`, `interactive`, `button`, `unsupported` are stored (`body` is kept for `text` and for the title of a tapped button or list row — `interactive.button_reply.title`, `interactive.list_reply.title`, `button.text` — otherwise `null`; the reply id from `interactive.button_reply.id`, `interactive.list_reply.id`, or `button.payload`, trimmed; blank or longer than 256 code points means no reply id (`null`), otherwise it is forwarded in the `ClientMessageReceived` event; `reaction`, `system`, unknown types and `statuses` are ignored; messages without non-blank string `id`, `from` or `type` are skipped);
  - client and conversation: a digits-only `from` (`1..15` digits) is normalized as `"+" + from` with the default region (or kept if already E.164); on the first message the client (`client_created` with actor `client`) and their single `conversations` row are created with the trimmed WhatsApp `contacts[].profile.name` (up to 100 code points; an existing client's name is never overwritten);
  - timestamps and idempotency: `messages.created_at` comes from the WhatsApp `timestamp` (epoch seconds, falling back to the server clock; never later than the server clock, a future timestamp is replaced by the receive time); only newly inserted messages advance `conversations.last_inbound_at` and `last_message_at` (`greatest`); retries and parallel deliveries are deduplicated by the unique `messages.wa_message_id` (`on conflict do nothing`).

## Sending messages

- `WhatsAppClient` ✅ — sends `POST {WHATSAPP_API_URL}/{WHATSAPP_PHONE_NUMBER_ID}/messages` with `Authorization: Bearer <WHATSAPP_ACCESS_TOKEN>` and returns the `messages[0].id` (`wa_message_id`).
- Message kinds (`OutboundMessage`, limits checked in code points before any HTTP request):
  - `Text`: body `1..4096` (`preview_url = false`);
  - `Buttons`: body `1..1024`, `1..3` reply buttons (`id` `1..256`, `title` `1..20`, both unique);
  - `ListMenu`: body `1..1024`, button label `1..20`, `1..10` rows in a single section (`id` `1..200` unique, `title` `1..24`, optional `description` `1..72`);
  - `Template`: name `^[a-z0-9_]{1,512}$`, language `^[a-z]{2,3}(_[A-Z]{2})?$` (`ru`, `en_US`), body parameters `1..1024` each without `\n`, `\t`, or 5+ consecutive spaces.
- Recipient: E.164 phone from `clients.phone` (`^\+[1-9][0-9]{6,14}$`), sent in `to` as digits without `+`.
- Timeouts and redirects: `app.whatsapp.api.connect-timeout` is `5s`, `read-timeout` is `15s` (each `> 0` and `<= 60s`); HTTP redirects are never followed.
- Empty environment variables: if any of `WHATSAPP_API_URL`, `WHATSAPP_ACCESS_TOKEN`, or `WHATSAPP_PHONE_NUMBER_ID` is empty, the API starts normally and `send` throws `WhatsAppSendException(NOT_CONFIGURED)` without making an HTTP request.
- Retries and error classification: the client never retries; failures are mapped to `WhatsAppSendException` (whose message never includes tokens, phone numbers, message text, or Meta's `error.message`) in this order:

  | Condition | `Reason` | `retryable` |
  |---|---|---|
  | `WHATSAPP_API_URL`, `WHATSAPP_ACCESS_TOKEN`, or `WHATSAPP_PHONE_NUMBER_ID` is empty | `NOT_CONFIGURED` | no |
  | no response: I/O error or timeout (`ResourceAccessException`) | `UNAVAILABLE` | yes |
  | HTTP `401` or Meta `error.code = 190` | `UNAUTHORIZED` | no |
  | HTTP `429` or Meta `error.code` in `{4, 80007, 130429, 131056}` | `RATE_LIMITED` | yes |
  | HTTP `5xx` | `UNAVAILABLE` | yes |
  | other HTTP `4xx` (including `131047` outside window and `131026` undeliverable; `131047` is turned into `OutsideWindowException` by `OutboundMessages`) | `REJECTED` | no |
  | HTTP `2xx` whose body cannot be read, has no non-blank `messages[0].id`, or is not valid JSON | `INVALID_RESPONSE` | no |

### Window and stored messages

- `OutboundMessages.send(conversationId, author, message)` ✅ — the only entry point for outgoing messages (`Author`: `BOT`, `MASTER`; returns `Sent(messageId, waMessageId)` with the stored `messages.id` and `wa_message_id`).
- Recipient: read from the conversation's client phone (`clients.phone`); an unknown `conversationId` throws `IllegalArgumentException` before any HTTP request.
- 24-hour window (`WhatsAppWindow`): open while `now < last_inbound_at + 24 h` (`Clock`); at exactly 24 h or later, or when `last_inbound_at` is `null` (no client message yet), the window is closed and only `OutboundMessage.Template` is allowed.
- `OutsideWindowException`: thrown for non-template messages outside the window before any HTTP request or database write, and also when WhatsApp rejects a send with Meta error code `131047` (with the `WhatsAppSendException` as cause).
- Storing accepted messages: written to `messages` only after WhatsApp accepted the send (`direction = 'out'`, `author` = `'bot'` or `'master'`, `body` = text / interactive body for `Text`, `Buttons`, `ListMenu` or `null` for `Template`, `wa_message_id` from the response, `created_at` from the server clock), deduplicated by `wa_message_id` (`on conflict (wa_message_id) do nothing`, returning the existing `messages.id` when it belongs to an outgoing message of the same conversation, or throwing `IllegalStateException` if `wa_message_id` is already stored for another message); `conversations.last_message_at` is advanced with `greatest(last_message_at, at)` only when a new row is inserted, and `last_inbound_at` is never changed.
- No database transaction during the HTTP request: reading the recipient/window and storing the message are single SQL statements, so the HTTP call never holds a database connection or lock; `send` refuses to run inside a database transaction (`IllegalStateException` before any database read or HTTP request).
- Failed sends (`WhatsAppSendException` or `OutsideWindowException`) are not stored and not retried; a send accepted by WhatsApp (`200`) whose database write fails afterwards propagates the error and is not resent.
- `conversations.human_mode` (checked by `BookingBot`) and delivery status webhooks (`statuses`) are not handled in `OutboundMessages`.

## Bot (button booking)

- `ClientMessageReceived(conversationId, clientId, waMessageId, text, replyId)` ✅ — published by `WebhookDeliveries` after `InboundMessages.store` commits and `webhook_logs` is saved, outside any database transaction, in delivery order, only for newly stored messages (never for duplicates or failed deliveries). Each listener call is wrapped in `try/catch`: a runtime exception is logged at `WARN` (exception class name only) without blocking subsequent events, and the webhook response is always `200`.
- `BookingBot` ✅ — synchronous `@EventListener` for `ClientMessageReceived`:
  - checks `settings.bot_enabled` and `conversations.human_mode`: silent when the bot is disabled, the conversation does not exist, or `human_mode` is `true`;
  - stores conversation state in `bot_sessions` (steps `menu`, `service`, `day`, `time`, `confirm`, `move_pick`, `cancel_pick`, `cancel_confirm`); a session lives for 24 hours (`updated_at + 24 h > now` from the API clock; at 24 h or older it restarts from `menu`);
  - saves the next state to `bot_sessions` before sending replies, so a failed send leaves the conversation on that step and the next client message repeats the prompt;
  - sends replies only through `OutboundMessages.send(..., Author.BOT, ...)` (called only by `BookingBot`), which refuses to run inside a database transaction (`IllegalStateException`);
  - delegates service, day and time list turns to `BotLists` and upcoming-appointment menu and cancellation turns to `AppointmentChanges`;
  - builds and parses all reply ids and message payloads in `BotReplies` (canonical `UUID`, `LocalDate`, `Instant`, `IdAndStart` (`<uuid>:<Instant>`), and a non-negative integer offset without sign or leading zeros; any unparsed or unexpected input on a step repeats that step's prompt):

    | `replyId` | Meaning | Step |
    |---|---|---|
    | `book` | `"Записаться"` | `menu` |
    | `cancel` | `"Отменить запись"` | `menu` |
    | `service:<uuid>` | active service (`UUID`) | `service` |
    | `more_services:<offset>` | `"Ещё массажи"`, next page of services | `service` |
    | `day:<yyyy-mm-dd>` | local day in `settings.time_zone` (`LocalDate`) | `day` |
    | `time:<Instant.toString()>` | appointment start in UTC (e.g. `time:2026-11-03T05:00:00Z`) | `time` |
    | `more_times:<Instant.toString()>` | `"Позже"` (`"Ещё время в этот день"`): times strictly after the given instant | `time` |
    | `other_day` | `"Другой день"` | `time` |
    | `confirm:<service uuid>:<Instant>` / `other_time` | `"Подтвердить"` (carries the service `UUID` and start `Instant` in UTC being confirmed) / `"Другое время"` | `confirm` |
    | `appointment:<uuid>` | upcoming appointment (`UUID`) | `cancel_pick` |
    | `cancel_confirm:<appointment uuid>` / `keep` | `"Отменить запись"` (carries the appointment `UUID` being cancelled) / `"Не отменять"` | `cancel_confirm` |

  - `menu` ✅ — queries up to 10 (`MAX_UPCOMING = 10`) upcoming confirmed appointments of the client via `AppointmentService.upcomingOfClient(clientId, 10)` (`AppointmentRepository.findConfirmedOfClientStartingAfter`: `client_id = :clientId`, `status = 'confirmed'`, and `lower(period) > now` from the API clock, ordered by `lower(period), id`; already started, past, cancelled, no-show, and other clients' appointments are excluded); when the client has none, sends `"Здравствуйте! Я помогу записаться на массаж."` with reply button `book` (`"Записаться"`); when the client has upcoming appointments, sends `"Здравствуйте! Я помогу записаться на массаж.\n\nВаши записи:\n<Weekday>, <d> <month>, <HH:mm> — <service title (≤ 24 code points with …)>"` (one line per appointment, formatted in `settings.time_zone`) with reply buttons `book` (`"Записаться"`) and `cancel` (`"Отменить запись"`);
  - `service` ✅ — on `replyId = "book"` from `menu` (or any non-matching input while on `service`), sends `"Выберите массаж из списка."` (button `"Выбрать массаж"`, active services in catalog order, row id `service:<uuid>`, title truncated to 24 code points with `…`, description `<duration> мин · <price> ₸` with non-breaking spaces; when up to 10 services remain from the page offset they are all shown, otherwise 9 services plus `"Ещё массажи"` with row id `more_services:<offset>` advancing to the next page, and an out-of-range offset returns to the first page), or returns to `menu` with `"Сейчас запись через бота недоступна. Мастер увидит ваше сообщение и ответит."` when no services are active; tapping `service:<uuid>` of an active service moves to `day` (an inactive or unknown service repeats the first page);
  - `day` ✅ — scans 30 local days starting from today in `settings.time_zone` (`today .. today + 29`) via `SlotService.freeStarts(serviceId, day)` and lists up to 10 days that have free start times (`"Выберите день."`, button `"Выбрать день"`, row id `day:<yyyy-mm-dd>`, title `"<Weekday>, <d> <month>"` in Russian such as `"Вторник, 3 ноября"`, description `"Сегодня"` / `"Завтра"` relative to today or `null`); if the service was deactivated (`freeStarts` returns empty) it returns to `service` (or `menu` with `"Сейчас запись через бота недоступна. Мастер увидит ваше сообщение и ответит."`), and if no day in the 30-day window has free time it returns to `menu` with `"В ближайшие 30 дней свободного времени нет. Мастер увидит ваше сообщение и ответит."`; tapping `day:<yyyy-mm-dd>` within `[today, today + 29]` moves to `time` for that day (if that day has no free times, sends `"В этот день свободного времени нет. Выберите другой день."` followed by the day list and stays on `day`; any other input or out-of-range date repeats the day list);
  - `time` ✅ — computes free start times in code via `SlotService.freeStarts(serviceId, day)` and sends `"<Weekday>, <d> <month>. Выберите время."` (button `"Выбрать время"`, up to 8 start times per page formatted as `HH:mm` in `settings.time_zone` with row id `time:<Instant.toString()>` in UTC and `null` description; if more than 8 remain, adds row `more_times:<8th-shown-instant>` with title `"Позже"` and description `"Ещё время в этот день"`; always ends with row `other_day` titled `"Другой день"` with `null` description, for at most 10 rows); `more_times:<instant>` shows times strictly after `<instant>` (falling back to the first page if none remain after it), `other_day` returns to `day`, and if the day has no free time left at all it sends `"В этот день свободного времени нет. Выберите другой день."` and returns to `day` (or `menu` if no free days remain); tapping `time:<instant>` whose local day in `settings.time_zone` differs from the session's day (a button from an older list) repeats the time list of the session's day without any extra text; otherwise it re-checks `SlotService.freeStarts(serviceId, day)`: if `<instant>` is still among the free starts it stores `start_at` in UTC and moves to `confirm` with `"Проверьте запись:\n<full service name>\n<Weekday>, <d> <month>, <HH:mm>\n<duration> мин · <price> ₸"` and reply buttons `confirm:<service uuid>:<instant>` (`"Подтвердить"`) and `other_time` (`"Другое время"`), otherwise sends `"Это время уже заняли. Выберите другое."` followed by the refreshed time list;
  - `confirm` ✅ — on `confirm:<service uuid>:<instant>` where `<service uuid>` equals the session's `service_id` and `<instant>` equals the session's `start_at` (`BotReplies.confirmationOf`), books through `AppointmentService.create(clientId, serviceId, start, AppointmentSource.BOT, EventActor.BOT, requestKey)` (`source = 'bot'`, `actor = 'bot'`) with an idempotency `RequestKey(BOT_REQUEST_USER, key)` derived from a fixed bot `user_id` (`UUID.nameUUIDFromBytes("massage-desk-bot")`) and `conversationId | serviceId | start | updated_at` of the loaded session, so a duplicate or concurrent tap returns the same appointment without creating a second booking or event, then resets the session to `menu` and sends `"Вы записаны:\n<full service name>\n<Weekday>, <d> <month>, <HH:mm>\n<duration> мин · <price> ₸\nЖдём вас!"` (formatted in `settings.time_zone`); on `BookingException` with `TIME_TAKEN` or `OUTSIDE_SCHEDULE` it sends `"Это время уже заняли. Выберите другое."` and returns to `time` for the session's day (or `day` / `menu` if no times or days remain), on `SERVICE_NOT_FOUND` it returns to `service` (or `menu` when no services are active), and on other booking reasons it returns to `menu`; `other_time` returns to `time` for the session's day, and any other input (including a confirm button for a different service or time, an old `confirm:<instant>`, or a bare `confirm`) repeats the current confirmation without booking;
  - `cancel_pick` ✅ — on `replyId = "cancel"` from `menu` (or any non-matching input while on `cancel_pick`, including `appointment:<uuid>` for another client's, past, already started, or cancelled appointment), loads the client's upcoming confirmed appointments (`upcomingOfClient(clientId, 10)`): if none remain, resets the session to `menu` and sends `"У вас нет предстоящих записей."` with reply button `book` (`"Записаться"`); otherwise (always shown even when the client has only one appointment) moves to `cancel_pick` and sends `"Какую запись отменить?"` (button `"Выбрать запись"`, row id `appointment:<uuid>`, title `"<d> <month>, <HH:mm>"` in `settings.time_zone` such as `"3 ноября, 10:00"`, description `"<Weekday> · <service name>"` truncated to 72 code points with `…`); tapping `appointment:<uuid>` of one of the client's own upcoming appointments (re-checked against a fresh `upcomingOfClient(clientId, 10)`) stores `appointment_id` in the session and moves to `cancel_confirm` with `"Отменить запись?\n<full service name>\n<Weekday>, <d> <month>, <HH:mm>"` and reply buttons `cancel_confirm:<appointment uuid>` (`"Отменить запись"`) and `keep` (`"Не отменять"`);
  - `cancel_confirm` ✅ — `keep` resets the session to `menu` and sends the current menu without changing the appointment; any other input where the reply id is not `cancel_confirm:<appointment uuid>` matching the session's `appointment_id` re-checks ownership against `upcomingOfClient(clientId, 10)`: if the appointment is still the client's own upcoming confirmed appointment it repeats `"Отменить запись?\n<full service name>\n<Weekday>, <d> <month>, <HH:mm>"` with buttons `cancel_confirm:<appointment uuid>` and `keep`, otherwise resets to `menu` and sends `"Эту запись уже изменили или отменили."` followed by the refreshed menu; on a matching `cancel_confirm:<appointment uuid>`, claims the step first via `BotSessionStore.claim(conversationId, Step.CANCEL_CONFIRM, updatedAt, now)` (`update bot_sessions set step = 'menu', service_id = null, day = null, start_at = null, appointment_id = null, updated_at = :at where conversation_id = :id and step = 'cancel_confirm' and updated_at = :updatedAt`): if 0 rows are updated (a concurrent tap already claimed the step), the turn returns empty without saving state or sending any message; after a successful claim, re-checks that the appointment is still among the client's own upcoming confirmed appointments (`upcomingOfClient(clientId, 10)`, with no minimum notice requirement before the appointment start): if not, sends `"Эту запись уже изменили или отменили."` followed by the menu; otherwise cancels via `AppointmentService.cancel(appointmentId, EventActor.BOT)` (`actor = 'bot'`) and sends `"Запись отменена:\n<full service name>\n<Weekday>, <d> <month>, <HH:mm>"` with reply button `book` (`"Записаться"`); on `BookingException` with `APPOINTMENT_NOT_FOUND` or `NOT_CONFIRMED` sends `"Эту запись уже изменили или отменили."` followed by the menu, and on any other `BookingException.Reason` returns to `menu`;
  - rescheduling (`move_pick` and the `day`/`time`/`confirm` steps with `appointment_id`) — planned (next part).
